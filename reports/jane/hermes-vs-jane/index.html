Hermes vs Jane: Would Hermes Alone Have Sufficed?

Critical technical analysis of building a cluster-native Jarvis/Friday from scratch (Jane) vs deploying Hermes Agent alone in a pod. Project: jane · 2026-08-03

TL;DR verdict

Partial yes, with sharp separation. If the goal is agentic devops + software development — an assistant that can execute on the cluster, write code, run pipelines — a bare Hermes pod would have delivered roughly 85–90% of the value with a fraction of the build effort. Jane's custom agent layer (turn orchestrator, dispatch handler, pipeline executor, progress manager, six workers, personality engine) was genuinely redundant: the project's own rearchitecture specs deleted ~2,000 lines of it the moment Hermes arrived.

But if the goal includes the Friday experience — live voice conversation, wake word, a web UI, identity and permission tiers — Hermes alone would not have been enough. Hermes ships zero voice stack, no browser UI, no multi-user auth, and no per-tier permission model. Those are real gaps, and Jane correctly owns them.

What was wasted: building the agent brain by hand. What was worth building: voice pipeline, PWA, PocketID auth + permission tiers, MCP tool server. What was arguably over-built for a single-user home lab: NATS as a central event bus, six background workers, a multi-runtime adapter registry, and a custom personality engine — all now replaced or superseded by Hermes-native features.

1. The question, stated precisely

Counterfactual: instead of building the Jane stack (bridge, speech service, PWA, Helm chart, guardians, NATS), would deploying hermes-agent (Nous Research, v0.19.0) as a single pod have achieved:

  • A Jarvis/Friday-style assistant living in the Kubernetes cluster
  • Complete “execute anything” control over the cluster
  • Software development driven through opencode
  • End-to-end devops (git → CI → deploy)

This is not hypothetical: Jane is already mid-migration to exactly this conclusion. Since 2026-07-25, the bridge has been re-architected so Hermes is the brain and the bridge is a thin gateway (config.ts: primary: "hermes"; hermes-adapter.ts calls the Hermes runs API; hermes gateway run on :8642 is the deployed brain). The report below evaluates the counterfactual as if that decision had been made first, and separates what Hermes natively covers from what Jane genuinely had to add.

3. What Jane adds on top (and why each exists)

Voice pipeline — NOT in Hermes

STT (faster-whisper) + TTS (Piper) in speech/, wired through speech-client.ts. Hermes' messaging platforms have voice notes at best; none give a real-time voice loop with streaming TTS mid-response. A Jarvis/Friday by definition needs this. Non-negotiable for the vision; Hermes alone fails it.

PWA (browser UI) — NOT in Hermes

React + MUI client: mic capture, wake word, PTT, chat store, tool-progress cards, approval dialogs. Hermes has no web UI — CLI, API, and messaging only. If the assistant is a companion app rather than a Telegram bot, this is a real build.

PocketID OIDC auth + 4 permission tiers — partially in Hermes

Hermes approval is binary (approve/deny a flagged command). Jane maps identity (JWT sub) to tiers (readonly → sandbox → devops → root) enforced at the WS layer and in the MCP tool server. For a home cluster where “full devops” means root-equivalent, tiered auth is a genuine safety addition, not gold-plating.

MCP server for Jane tools — gateway needed

41 tools (B-code, git, time, monitoring, vision, document, learning, context, Vikunja, smart home, email, calendar, MQTT) exposed on bridge :3002. Hermes is an MCP client; the server side for custom capabilities is always yours to build — either as a Python Hermes plugin or an MCP server (Bridge chose TS).

Guardians (4 actors) + autonomous safety — replicable in Hermes

Speech/bridge/infra/identity guardians watch and self-heal; autonomous-safety.ts adds dedup, rate limits, concurrency caps, circuit breakers. Hermes cron + webhooks + skills could approximate the scheduling, but the guardrail logic is custom work either way.

NATS event bus (10 streams) — likely over-built

Decouples bridge ↔ speech events. Useful infra learning; for a single-user assistant it adds a moving part that Hermes cron/webhooks largely replace. The 2026-07-30 spec itself narrows NATS' role to speech events and consolidation.

5. Aspect-by-aspect critical analysis

5.1 Capabilities

Hermes' breadth (70+ tools, MCP client, skills, cron, memory, messaging) covers nearly everything Jane planned under Plans A/B — the 2026-07-30 spec marks most Plan A/B tasks SUPERSEDED. The honest read: Jane was building, from scratch, an agent platform that already existed and was more mature (17k commits). The capabilities Jane kept that Hermes lacks are exactly the physical/experiential ones: voice, browser UI, and a tiered authz boundary around infrastructure control.

5.2 Effort and complexity

The strongest evidence: the rearchitecture spec (“~2000 lines removed, ~100 lines added”) deleted turn.ts, dispatch-handler.ts, pipeline-executor.ts, progress-manager.ts, opencode-client.ts, pi-adapter.ts, personality/, and all six workers. That is the exact surface the user asked “would Hermes have covered?” — and the project answered yes by deleting it. The wasted-build cost was real: those files took days each, and their tests now ship in git history only.

Conversely, the pieces that survived rearchitecture (WS server, speech client, auth, permissions, guardians, capabilities) are precisely the ones Hermes could not supply. The effort split was not misallocated overall; it was misallocated in the agent layer.

5.3 Safety (the strongest argument for Jane's layers)

Complete cluster control means a single hallucinated kubectl delete or unguarded git push --force can take down production. Jane's mitigation stack:

  • Tiered auth (readonly/sandbox/devops/root) mapped from PocketID identity, enforced at WS and MCP tool layer
  • Autonomous loop safety: dedup by event ID, rate limit (5/min/rule), concurrency cap (3), circuit breaker (3 failures → 5min cool-off)
  • NATS autonomous.audit decision trace for forensics

Hermes' approval.py is a per-command human gate — good, but binary and single-user. The 2026-07-30 plan-critique flagged exactly these gaps (git without safety gates, autonomous infinite loops, no cost control). Bottom line: a Hermes-only deployment is viable only if you add an authz/guardrail layer on top. That is not “building Jane”; it is a small, well-scoped addition.

5.4 Ops and maintenance

  • Image weight: Hermes is Python — ~2–5GB vs Node ~200MB (noted in spec). Separate deployment with resource limits required.
  • SQLite single-writer → single replica (same constraint as PocketID). Acceptable for one user; rules out HA without redesign.
  • Upstream churn: pin hermes-agent==0.19.0; test upgrades. MIT but fast-moving.
  • Logging fix is trivial: symlink $HERMES_HOME/logs → stdout; Loki picks it up.
  • Config-as-code: skills, cron, and SOUL.md are files on a PVC / in the image — GitOps-friendly.
  • Fewer components to run: Hermes-only replaces ~6 worker processes and a runtime registry with one pod.

5.5 Cost

Hermes-only eliminates: bridge agent-layer code, 6 workers, personality engine, multi-runtime adapters — ongoing maintenance and test burden. It keeps: model API costs (unchanged), storage (SQLite on PVC + mem0). The 2026-07-30 spec adds a needed cost control (MAX_LLM_CALLS_PER_HOUR) because autonomy multiplies LLM calls — a gap Jane had flagged but not yet closed. So Hermes-only is cheaper to build and run, but requires one new budget guard.

5.6 Extensibility

Hermes wins on breadth (MCP client, skills, provider routing) but constrains you to its plugin API (Python) and its session/storage model. Jane's TS MCP server keeps custom tools in one codebase with type safety and the tier check inline — a cleaner extension path for Jane-specific integrations (Vikunja, smart home, MQTT, calendar). For a home-lab with bespoke tools, a thin MCP gateway is still the right pattern; it just doesn't need to be 2,000 lines of orchestration.

5.7 Learning value (the honest counterweight)

Building Jane the long way produced durable platform assets: the self-hosted stack (mem0 server + plugin, PocketID, Flux + Helm chart, CI multi-arch pipeline, skills for patrick-jane-scholar), plus hard-won cluster knowledge (Flannel/CoreDNS, cert-manager token scoping, SQLite storage-class rules) that the infra context now codifies. None of that comes from installing hermes-agent. So “should have just done Hermes” is correct for the agent, not for the platform education. The economically rational path was: Hermes pod day 1 for the brain, invest the saved effort in the voice/UI/auth layers and the self-hosting platform — not in re-deriving an agent loop.

Two specs, one conclusion, already implemented: deleted custom agent layer, AGENT_PRIMARY=hermes, hermes-adapter.ts driving the runs API, mem0 provider plugin, patrick-jane-scholar skill + daily cron, MCP server on bridge :3002 for Jane tools. The counterfactual the user is asking about is, in effect, the plan the project adopted — retroactively applied to the starting line.

7. The minimal viable alternative (what should have been built)

  1. Hermes pod (hermes-agent, pinned) + PVC for $HERMES_HOME — the brain. Wire mem0 as memory provider, add skills + cron. ~1 day.
  2. Thin voice gateway — STT/TTS service + WS endpoint translating speech ↔ Hermes runs API + SSE. Keep this; it's the Friday part.
  3. Small MCP server for Jane tools (Vikunja, smart home, MQTT, git/gh/kubectl wrappers) with tier checks. Keep this.
  4. OIDC auth + tier header (PocketID) mapped into Hermes via X-Jane-Permission, enforced by approval system + MCP layer. Keep this.
  5. Minimal PWA — chat + voice + approval dialogs. Keep this, scoped.
  6. Skip until needed: NATS central bus, six workers, multi-runtime registry, custom personality engine, custom pipeline/progress machinery.

Rough net: ~60–70% less code than the as-built Jane, delivering the same assistant experience, because the agent brain was the biggest single chunk of rebuilt-from-scratch logic.

8. Risks of the Hermes-only path (if taken blind)

  • Unbounded cluster access. Mounting a kubeconfig into an agent that can run any terminal command, without tiered authz + audit, turns a hallucination into an incident. Non-negotiable add-on.
  • Autonomy feedback loops (alert → diagnose → new alert → new session) without dedup/rate-limit/circuit-breaker. Documented in plan-critique.
  • Cost runaway from autonomous loops — needs a call budget.
  • Voice expectation mismatch. If the user expects “Friday” and ships Hermes alone, they get a Telegram bot — powerful, but not the vision.
  • Single-writer SQLite — no HA; acceptable for one user, a trap if scaled.

9. Bottom line

Yes — for the agentic core. Hermes in a pod would have handled opencode-driven development, end-to-end devops, and “execute anything” on the cluster, plus delivered more (messaging reach, skills, subagents, model routing) than Jane's original custom agent layer. The rearchitecture that deleted that layer is the project's own admission.

No — for the assistant experience. Voice, browser UI, and tiered multi-user authorization are not in Hermes and never would be; those justify the speech service, PWA, auth, and MCP gateway.

Recommendation for the future: continue the current trajectory — Hermes as brain, Bridge as thin gateway — and treat any new capability as a skill, cron job, or MCP tool on Hermes rather than bridge orchestration code. Put the saved engineering time into the layers Hermes cannot provide: voice quality, UI, and permission UX.
